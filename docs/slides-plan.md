# 方案：这篇 → 幻灯片（北极星痛点 6，只出方案不改代码）

> 第 581 轮（2026-09-14）。痛点 6 的原话是「**想做成 PPT，又要上传给另一个 agent 工具，
> 两个工具之间没有链接**」。它是 13 个痛点里唯一没有落点的：现在只有模型自己调
> `run_skill_script` 去跑第三方 skill 生成 .pptx 那条路（沙箱里跑得起来，但没有按钮、
> 没有判据、产物也回不到笔记里）。

## 一句话设计

**产物是一篇「幻灯片笔记」，不是一个文件。** 用 Marp 风格的 markdown（front-matter +
`---` 分页）落成原笔记的一个子笔记，于是它天然继承这个产品已有的一切：能用 ⌘K 找到、
能挂引用、能被智能续写继续改、能进知识库、能导出。**导出成 .pptx / PDF 是第二步**，
不是主路径——主路径要解决的是「两个工具之间没有链接」，而不是「我要一个 pptx 文件」。

为什么不直接生成 .pptx：那等于把内容送出这个编辑器，回不来；改一个字要重跑一遍；
而且 python-pptx + 模板是一整套新依赖。Marp markdown 是纯文本，改一个字就是改一个字。

## 落点

| 层 | 改什么 |
|---|---|
| 入口 | 正文右上角「更多动作」菜单加一项「做成幻灯片」；`/` 菜单加 `slides`。判据 1：一个能力一个按钮，不是聊天框 |
| 接口 | `POST /api/compose/slides`（SSE，跟 magic tap 同一条流的形状）：入参 `note_id` / `content` / `scope` / `style`（`要点` \| `讲稿`），出参 delta + 最后一个 `slides` 事件带页数和判据 |
| 生成 | 一次模型调用，不进 harness 多轮循环——幻灯片是一次成型的重构，多轮只会把页越改越碎。prompt 见下 |
| 落库 | `store.create_note(user, f"{原标题} · 幻灯片", md, parent=原笔记)`，图标 `bx-slideshow`；原笔记正文不动 |
| 判据 | 新 `harness/checks/slides.py`，全是确定性的（见下）。不合格不拦着落库，跟着产物一起显示，用户自己决定要不要重跑 |
| 预览 | 右栏新面板「幻灯片」：按 `---` 切页、纯 CSS 画 16:9 的缩略图，不引 Marp（那是 600KB+ 的依赖，只为预览不值）。点一页跳到正文对应位置 |
| 导出 | 「导出」菜单加「幻灯片 → PDF」：Electron 主进程 `win.webContents.printToPDF` 打预览页，零新依赖。`.pptx` 留给第三方 skill 那条路（已经能跑），在导出菜单里给一个「用 skill 生成 .pptx」的入口 |

## prompt 要点（`harness/prompts/slides.py`）

- **每页只讲一件事**：标题是一个完整的判断句（「EVT 节点从 6 月挪到 8 月」），不是名词短语（「EVT 节点」）
- **正文里的引用标记原样带到对应页**——这是这个产品跟通用 PPT 工具的根本差别：每一页都能点回它的依据
- 正文里已有的 ```mermaid 图整块搬到它该在的那一页，不要重画
- 每页要点 3–5 条、每条不超过 40 字；超了就拆页，不要缩字
- 首页 = 标题页（笔记标题 + 一句话结论），末页 = 「还缺什么」（正文里 `待核实` / 没有引用支撑的判断）
- 页数按内容定，通常 8–20；正文很短就少给，不要注水

## 判据（`checks/slides.py`，零模型调用）

| 判据 | 怎么判 | 为什么 |
|---|---|---|
| `cite_coverage` | 有引用标记的页 / 总页数 | 痛点 6 要的是「有链接」，一页没有依据的幻灯片就是通用 PPT 工具的产物 |
| `page_density` | 每页正文字数 ≤ 200、要点 ≤ 6 条 | 一页塞一屏字是 PPT 最常见的坏味道，确定性可判 |
| `title_is_a_claim` | 每页标题是否含谓词（启发式：有没有动词 / 数字 / 「是\|要\|从\|到」） | 名词短语标题读者要自己猜结论 |
| `source_fidelity` | 幻灯片里出现的数字是否都能在原文里找到 | 复用 `checks/citations.py` 那套数字比对，防止总结时把数字改了 |
| `covers_the_note` | 原文各个 `##` 小节是否都有对应页 | 漏掉整整一节是真实风险 |

- 打桩一次模型调用，跑通 `/api/compose/slides` 的 SSE 形状 + 落库 + 父子关系
- 真跑一次：拿 `5f65df10cad6` 生成，人看 8–20 页、引用带没带过去、mermaid 有没有重画
- 前端：预览面板的分页纯函数进 vitest（`---` 在代码块里不算分页符——跟 `sectionEnd` 同一个坑）

## 不做的

- 不做主题 / 配色选择器：一套跟应用同源的样式就够，选主题是 PPT 软件的活
- 不做「反向同步」（改幻灯片回写笔记）：两份内容的同步是个没有好答案的问题，幻灯片是笔记的**导出物**，要改改笔记再重生成
- 不把幻灯片做成一种新的笔记类型：它就是一篇 markdown 笔记，front-matter 里一个 `slides: true` 足够让预览面板认出它

## 落地记录（第 648–651 轮，2026-09-14）

四件都做完了：入口（⋯ 菜单）/ 生成 + 判据 / 右栏预览 / 导出 PDF。跟上面这份方案的差别记在这儿：

|---|---|---|
| `/` 菜单加 `slides` | **没做** | `/` 菜单每一项都是「在光标这个位置插入点什么」，而做成幻灯片是**另起一篇笔记并跳过去**。加进去会破坏那个菜单自己的规矩；而且这个动作已经有一个门了——**同一个动作别开三个门**（第 625 轮用户原话） |

| `covers_the_note` 按小节标题比 | 再看一眼**这一节的引用编号有没有进到幻灯片里** | 按标题比误报 3 节，而那 3 节的引用 6/6、4/5、18/21 都进去了——内容进去了就不算漏 |
