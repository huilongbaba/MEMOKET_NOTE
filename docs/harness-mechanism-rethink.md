# harness 机制本身：重新想一遍

> 第 755 轮。**方案文档，不改代码。**
>
> 上一份（`harness-effect-plan.md`）是七处堵漏。堵漏的隐含前提是
> 「机制是对的，只是执行有缺口」。把回路从头读一遍之后我不这么认为了：
> **有三处结构性错配**，不动它们，补上的缺口只会把症状挪个地方。
>
> 这份不推翻上一份——上一份的数据全部还成立，
> 而且下面每一条都是**由那批数据反推出来的机制解释**。

---

## 一、一轮里有三个动作，其中两个只会让文本变长

一轮的实际形状（从 `loop.py` 读出来）：

```
gather（检索）→ revise（改已写的，上限 6–10 处）→ produce（续写，不封顶）→ judge（对整篇打分）
```

三个动作里，**只有 `revise` 能让文本变短或变对**。`gather` 和 `produce` 都只能让它变长。

而维度天然分成两族，代码里其实已经分好了：

| 族 | 代码里的名字 | 追加对它 |
|---|---|---|
| 覆盖度 | `loop.py:329` `COVERAGE_DIMS` = beat_coverage / section_coverage / material_use | **只会变好** |
| 内在质量 | `repair.py:27` `INNER_QUALITY` = non_repetition / coherence | **只会变差** |

实测数据跟这个划分**严丝合缝**：

```
material_use（覆盖度）     25 次里 24 次满分
non_repetition（内在质量）  29 次里  9 次不达标
coherence  （内在质量）     29 次里  8 次不达标
```

### 错配一：最弱维度的诊断被送去了检索规划

`loop.py:145` 算出 `steer`（最弱维度 + 打分模型自己写的那句诊断），
经 `policy.steer` 到 `hooks/note.py:147` —— 进的是 **`retrieval_plan_user`**，
也就是「这一轮该查哪些事实」那个 prompt。

**检索能修的只有 `factual_grounding` 和 `material_use` 两项。**
当最弱维度是 `non_repetition` 时，「你把同一件事说了两遍」这句诊断
进的是一个决定去知识库查什么的 prompt。查什么都修不了重复。

`focus_note` 走的是另一条线（`revise.py:72`），那条是对的。
但两条线的力气不对等：**修订上限 6–10 处，续写不封顶。**

## 二、修复那条路是通的，但通到一半断了

必须说清楚：**架构已经想到了这件事。** `repair.py` 的模块注释写得比我清楚：

> a coverage dimension is weak -> write more；
> an inner quality dimension is weak -> fix it, and add nothing。
> Continuing when the problem is repetition cannot work.

它的做法是把下一轮标成 `cleanup_only`（`repair.py:78`），
那一轮 `produce` 直接返回（`hooks/note.py:220`、`hooks/section.py:125`；`prepare` 也一起跳过，`note.py:112`），只跑修订。

**那为什么 `non_repetition` 还是一路掉到 0？** 把这条路走一遍就看见断口了：

```
判分：non_repetition = 0
  ↓  Repair：下一轮 cleanup_only          ✅ 决策正确
  ↓  revise 拿候选对：st.bag["dup_hints"]
  ↓  dup_hints 来自 repeats.py:57 find_repeats
  ↓  _paragraphs = text.split("\n\n")      ← 段落级
  ↓  而真实产出里的重复是【段内】的        ← 实测 42.9%
  ↓  候选对 = 空。修订这一轮无事可做
  ↓  st.fresh 空 + revisions_applied 0
  ↓  loop.py:_no_progress → 停机
```

**回路恰好在修复机制该起作用的那一刻停机。**
而且它停下来的时候，`no_progress` 这个理由读起来像「已经收敛了」——
实际上是「修理工到了现场，但没人告诉他哪里坏了」。

这条链解释了上一份里那个 54%：停在 `continue`、
而 `non_repetition` / `coherence` 正是第 2、第 3 大阻塞项。

### 由此得到一条可以直接拿去查的设计规则

> **每一个「内在质量」维度，必须配一个能指到具体位置的机械探测器。
> 没有探测器的维度，它的分数只能让回路停下来，不能让它变好。**

按这条规则查现状：

| 维度 | 探测器 | 能指到具体位置吗 | 实测不达标 |
|---|---|---|---|
| `non_repetition` | `find_repeats` | **段级——段内失明** | 9 / 29 |
| `coherence` | **没有** | 否 | 8 / 29（3 次 0 分） |
| `topic_fidelity` | **没有** | 否 | 7 / 16 |

`coherence` 拿过 3 次 0 分，而**这个系统里没有任何一行代码能说出它不连贯在哪**。
那 3 次 0 分对回路的唯一作用是：触发 `Repair` → `cleanup_only` → 修订没有候选 → 停机。

## 三、`coherence` 同时是一个维度和一个兜底桶

`checks/pick.py` 的 `pick_dimension(st, 首选, 次选, 三选)` 会挑模式里存在的第一个。
统计所有判据的落点：

```
6 条判据把 coherence 写在第二或第三位
（has_charts→coherence、table_validity→coherence、
  style_fit→coherence、fits_context→coherence、non_repetition→coherence …）
```

于是 `coherence = 0` 可能意味着：审计腔、手写 mermaid、标题位置不对、
表格不合法……**也可能真的是文章不连贯**。而 `Repair` 一律读成
「这一轮只修不写」。

代码里已经记着这么死过一次（`repair.py:42`，第 606 轮）：
判据说「去调工具把图画出来」，修复策略说「这一轮不许写」，
两轮原地打转、一分没得，最后 `no_progress` 收场。
当时的修法是「判据命中的那一轮不算数」——**治了那一次，没治病根。**

> **一个维度不能既是优化目标又是垃圾桶。**
> 目标要有可操作的含义；垃圾桶只需要有个地方放。

---

## 四、`topic_fidelity` 是个孤儿

它不在 `INNER_QUALITY`，也不在 `COVERAGE_DIMS`。
7/16 不达标，而**两条执行器选择规则都不看它**：
既不会触发「只修不写」，也不算「还没写够」。
它能做的只有把 `status` 钉在 `continue` 上，然后看着回路跑满轮数。

而它本质上是内在质量的：**已经跑题的那段文字，不会因为后面补了几段
切题的就不跑题了。**

---

## 五、更深一层：这个回路没有 ground truth

前面四条都还是「执行器和目标对不上」。再往下一层是：**目标本身从没被校验过。**

没有任何证据表明「五个维度全 2 分」等于「用户愿意留下这篇笔记」。
而 Goodhart 已经发生过，代码里自己记着（`best_of.py` 开头）：

> round 2 produced two clean charts, round 3 added a single-value bar
> **to satisfy the scorer**, round 3 was delivered.

**唯一真实的信号，是用户拿到结果之后对它做了什么。**
`note_revisions` 这张表已经在了，但现在只有 30 行、9 篇，
而且**跟哪一次跑无关**——用不了。

这件事的份量跟前面几条不一样：前面是「把断掉的线接上」，
这一条是**把整套判据从「断言」变成「被验证过」**。
做法不复杂：跑完落一份正文，用户下一次保存再落一份，
**这两份之间的 diff 就是标注**——他删掉的那几段，
就是那一轮打了 2 分而实际不合格的地方。
攒够之后能回答一个现在完全答不出的问题：
**哪几个维度真的预测用户会删。**

## 六、轮次是前缀嵌套，所以 `best_of` 只能截断

长文模式下 `produce` 是追加（`types.py:68`：`st.content = join(st.content, 新写的)`），
所以**第 N+1 轮的正文包含第 N 轮的正文**。

于是「挑最好的那一轮」实际上是「决定在哪儿停」——
它永远只能**扔掉**后面几轮的工作，不可能把第 3 轮的好段落
和第 2 轮的干净结构**组合**起来。

block 模式是 `st.content = 新块`（替换），那里的 `best_of` 是名副其实的。
长文这里名不副实，**而长文正是它最被指望的地方**。

---

## 七、成本从不进入停机决策

`judge` 只说 continue / complete / blocked，不问「再花十几秒值不值」。
而数据是反的：

```
跑 1 轮   17 次   达标 53%
跑 2 轮   10 次   达标 30%
跑 3–4 轮  7 次   达标 29%
```

**这不是「轮数不够」，是「继续」这个决定本身缺一个收益预期。**

---

## 改法：三层，顺序不能反

### 第 0 层：先能看见（否则下面全是猜）

- 每轮分数落库（上一份 P3）。**这一层不落，第 1、2 层改完都无法证明变好了。**
- 停机原因单独记一列（上一份 P4）：现在 `no_progress` 和 `max_rounds`
  混在同一个 `continue` 里，而第二节说明了这两者含义完全相反。

### 第 1 层：把断掉的那条线接上（改动小、因果清楚）

1. **`find_repeats` 增加句级一趟**（`repeats.py:57`）。
   这是第二节那条链上的断口，一处修好，`Repair` 那条正确的决策才落得了地。
   阈值在 18 篇真产出上量，**误伤比漏报贵**。
2. **`topic_fidelity` 归进 `INNER_QUALITY`**（`repair.py:27`）。
   一个元组加一个词，但它把 7/16 的不达标从「只能让回路停下来」
   变成「能触发一次只修不写」。
3. **`steer` 分流**（`hooks/note.py:147`）：只有 `factual_grounding` /
   `material_use` 这两族的诊断该进检索规划；内在质量那族的诊断
   进检索 prompt 是纯噪声，应当只走 `focus_note` 那条线。

### 第 2 层：机制（要先有第 0 层的数据才能验）

4. **给 `coherence` 拆出兜底桶**。新增一个不参与 `Repair` 决策的
   `mechanics` 维度（或直接让判据命中不再伪造 Evaluation，走独立通道），
   让 `coherence` 只表示「文章读起来顺不顺」。
   *现状的补丁（「判据命中那一轮不算数」）会跟着一起退休。*
5. **内在质量维度必须有探测器**，否则不许进 `INNER_QUALITY`。
   `coherence` 现在没有——要么补一个能指到位置的（段落间话题跳变、
   代词悬空、时间线倒序都是可机械检测的），要么承认它只能用来**停机**
   而不能用来**驱动修复**，并在代码里写明。
6. **采集人的信号**：跑完落一份正文，用户下次保存再落一份，
   跟 `harness_runs` 关联。这是第五节那件事，也是唯一能让
   「判据到底对不对」这个问题有答案的做法。

### 我建议的落地顺序

```
0 层（看见）→ 1.1（段内查重）→ 1.2 + 1.3（两个小改）→ 验一轮 → 6（采集人的信号）→ 2 层其余
```

第 6 条要尽早开始**采集**（采集本身没有风险），
但**不要急着用它改判据**——样本不够时按它调参，比不调更糟。

## 明确不建议做的

- **不重写 `loop.py`。** 上面七条一条都不需要动循环本身。
  这份代码被「一个 harness 有另一个没有」的 bug 教育过四次，
  它现在的形状是那四次的结果。
- **不加新维度。** 现在已经有 ≥5 个从不区分好坏的维度（上一份 ②）。
  问题是**执行器**不够，不是**指标**不够。
- **不做自动回滚 / 自动删重复。** 段内句级相似是语义判断。
  上一份说过一次，这里再说一次是因为第 1 层的改动会让人很想顺手加上。
- **不把「继续还是停」交给模型再判一次。** `policy.py` 开头已经论证过：
  不可复现、无法归因。第七节那个「收益预期」应该是从第 0 层数据里
  **学出来的一条规则**，不是再打一次模型。
- **不因为 `coherence` 分数低就加重它的权重。** 第三节说明了那个分数
  现在没有可操作的含义——在含义修好之前调权重，是在放大噪声。

---

## 改完怎么算有效

| 判据 | 现在 | 目标 |
|---|---|---|
| `cleanup_only` 轮里修订候选为空的比例 | **未测**（第 0 层之后可测） | < 10% |
| 因 `no_progress` 停机、且该轮是 `cleanup_only` 的次数 | **未测** | 0 |
| 段内重复字占比（18 篇产出上量） | 最差 **42.9%** | 最差 < 10% |
| 反复跑同一篇，分数单调下滑的比例 | **3/6** | 0/6 |
| 没有位置级探测器的内在质量维度个数 | **2**（coherence、topic_fidelity） | 0 |
| 判据与「用户是否删掉这段」的相关性 | **没有数据** | 有数据 |

回归照旧：`npm test`（254 vitest + 28 项脚本）、后端 `pytest`（1119）。
第 1.1 条的阈值按 `_corpus.mts` 那条规矩验**空泛性**：
在真实语料上「一条都不命中」和「全部命中」一样说明判据没用。
