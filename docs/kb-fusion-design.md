# 知识库 × 笔记：融合设计

> 用户要求：「你的 note 列表最好与知识库关联起来，两者能够很好的、很自然的
> 融合体验」。这份文档是那个设计。

## 1. 现状：两个互不相识的世界

| | 笔记 | 知识库 |
|---|---|---|
| 是什么 | 用户写的 markdown | 从摄入材料里**抽出来的**事实 |
| 存哪 | sqlite `notes` + `branches` | KITE codebook（XML） |
| 量级 | 几十到几千 | 几千到几万条事实 |
| 谁写的 | 人 | 机器（可回溯到原始对话行） |

它们之间现在只有**两条单向的细线**：
- 「存入知识库」：把一篇笔记摄入成事实
- 正文里的 `[fact-id]`：引用一条事实（刚做了悬停 peek）

**问题**：这两条线都不留痕。摄入过的笔记看不出摄入过；被引用的事实不知道
谁引用了它。于是两个世界各走各的，用户得自己在脑子里记住它们的关系——而
那正是判据 2 要省下的注意力。

## 2. 融合的骨架：双向链接

一条 `note ⇄ fact` 的双向链接，是整个融合的承重墙。

```
笔记 ──引用──> 事实        正文里的 [terrence-1872-5F8]
笔记 <──来源── 事实        这篇笔记被摄入后抽出了这些事实
事实 ──反查──> 笔记        哪些笔记引用了我  ← 现在完全没有
```

**为什么反查是关键**：Trilium 的右栏有 Backlinks（谁链到了这篇）。对我们
来说，「哪些笔记用到了这条事实」回答的是一个真问题——**这条事实是否还活着、
改了它会影响谁**。没有反查，知识库就是个只进不出的仓库。

### 落地：`note_citations` 表

```sql
note_id  TEXT   -- 哪篇笔记
fact_id  TEXT   -- 引用了哪条事实
```

**在保存笔记时扫正文重建**（不是让用户维护）。理由：引用写在正文里，正文
才是唯一真相；维护一张手工的关联表迟早跟正文对不上。

`notes` 上再加一列 `ingested_at`：这篇被摄入过没有、什么时候。

## 3. 界面上怎么体现

### 3.1 树上看得见

| 标记 | 含义 |
|---|---|
| `⧉` | 克隆（已有） |
| `◆ N` | 这篇引用了 N 条事实 |
| `⇡` | 这篇已经摄入进知识库 |

一眼看出哪些笔记「有据可依」、哪些还只是草稿。

### 3.2 知识库是树上的一棵虚拟子树

```
知识库/
├── 主题/     ← KITE 的 topic 本来就是层级的，直接当树
│   └── 众筹/ → 事实…
├── 实体/     ← 人、产品、公司
├── 时间线/   ← 按月聚合
└── 最近摄入/
```

**虚拟 = 不落库**，只是把 KITE 的数据呈现成树。收益是白拿的：标签页、
右栏、⌘J 跳转、右键菜单——这些肌肉记忆对知识库同样生效。

### 3.3 打开一条事实 = 打开一篇只读笔记

```
┌─────────────────────────────────────┐
│ 2026-06 · plan · 置信度 med          │
│ 2.0版本的时间先放6月30，众筹开始前… │
├─────────────────────────────────────┤
│ 原话                                 │
│ ▏Speaker A: 那这个就基本上已经…      │
├─────────────────────────────────────┤
│ 被这些笔记引用                       │  ← 融合的关键
│ · 创业一年回顾                       │
│ · 众筹节奏复盘                       │
├─────────────────────────────────────┤
│ 相关事实（同主题 / 同一次会议）      │
└─────────────────────────────────────┘
```

### 3.4 笔记的 ribbon 加一个「知识库」标签

这篇笔记跟知识库的**全部关系**，一处看全：
- 引用了哪几条（可点开 peek）
- 摄入过没有、抽出了多少条事实
- 有没有引用了**已经不存在**的事实（模型编的、或者知识库重建过）

### 3.5 右栏加「反向链接」

打开一条事实时显示「谁引用了我」；打开一篇笔记时显示「哪些笔记引用了这篇
摄入出来的事实」。对标 Trilium 的 Backlinks。

## 4. 查询与可视化要补的

现有的（`/api/kb/*`）都还在，但缺入口和打磨：

| 已有 | 状态 | 要做的 |
|---|---|---|
| 主题簇 clusters | 有接口没入口 | 进虚拟子树的「主题」 |
| 覆盖度 coverage | 有接口没入口 | 知识库首页的一块 |
| 抽取质量 quality | 有接口没入口 | 摄入完成后自动显示打了多少分（判据 3：自检要看得见） |
| 时间线 timeline | 有面板 | 进虚拟子树 |
| 知识图谱 | 弹层 | 进右栏「笔记图」 |

## 5. 明确的取舍

- **事实不复制成真笔记**。上万条塞进笔记树，树就废了。
- **引用不做成手工维护的关联**。正文是唯一真相，扫正文重建。
- **不给知识库做聊天框**。判据 1。查询靠：树导航、⌘K 搜索、选区「来龙去脉」。
