# 设计 v2：v1 + 定点修复

v1 的自查 15/15 通过，模式选对了。v2 加两件调研后期才发现的事。

## 新增 A：判据尽量往早了放（三个拦截点）

同一个缺陷，越早拦越省。我们其实已经在三个位置都拦过，但没当成原则：

| 位置 | 谁拦 | 成本 | 真实例子 |
|---|---|---|---|
| **工具层**（最早） | 工具拒绝产出坏东西 | 零 | `chart_from_text` 拒绝混量纲 `[10 倍, 576 台]`、拒绝单值图 |
| **检查层**（中） | 产出后代码判定 | 零 | `blockcheck` 抓假图、手写 mermaid、标题层级 |
| **打分层**（最晚） | 模型判定 | 一次 LLM 调用 | `has_charts`、`honest_caveats` |

**原则：能在工具层拒绝的，不要留到检查层；能在检查层判的，不要留给打分器。**
现在的顺序还反着——先打分（贵）再跑确定性检查（便宜），检查命中的话那次打分
就白花了。PydanticAI 的两阶段验证是反过来的：语法（零成本）先、语义（要 I/O）后。

## 新增 B：失败了怎么修，分三档

现在只有一档：不达标 → `steer` → **整轮重来**。代价实测到了——某次第 2 轮
画出两张干净的图，第 3 轮为了满足打分器又加一张单值图，交付第 3 轮。
**整轮重来会把已经好的部分一起重做。**

参考 writing-harness 的「按失败维度定点回滚」和 linter 的 auto-fix：

| 档 | 怎么修 | 成本 | 例子 |
|---|---|---|---|
| **1. auto-fix** | 代码直接改 | 零 | 标题层级过浅 → 直接降级；空壳标题 → 直接删 |
| **2. 定点重做** | 只重跑一个步骤 | 一次调用 | 没画图 → 只跑画图那步，文字不动；没说样本量 → 只补一句 |
| **3. 整轮重来** | 现状，兜底 | 全轮 | 跑题、结构性问题 |

表达方式（Check 带 fix，像 linter；Dimension 声明失败时重做哪一步）：

```python
@dataclass(frozen=True)
class Verdict:
    dimension: str
    message: str                      # 给模型看的话
    fix: Callable[[str], str] | None  # 能直接改就给一个纯函数，像 eslint --fix

Dimension(name="has_charts", guidance="...",
          on_fail=Repair.step("draw_charts"))     # 定点重做这一步
Dimension(name="coherence",  guidance="...",
          on_fail=Repair.FULL_ROUND)              # 兜底
```

## 自查 A：我们真实的失败案例，各归哪一档

全部取自本次会话的实测产出：

| 真实失败 | 档 | 说明 |
|---|---|---|
| 8 个 `###` 塞在 `##` 下面 | **auto-fix** | 代码直接降级，不必让模型重写 |
| 自带「接下来值得看什么」跟后文 `## 下一步计划` 撞 | **auto-fix** | 直接删这一节 |
| 通篇没图 | **定点** | 只跑画图那步 |
| 「昇腾 38%」主角没进图 | **定点** | 只重画那一张 |
| 没说 n=6 样本量小 | **定点** | 只补一句 |
| 假图 `[柱状图：…]` | **定点** | 必须调工具重画 |
| 手写 mermaid（y 轴带范围） | **定点** | 重新调工具 |
| 混量纲 `[10 倍, 576 台, 4 台]` | **工具层已拦** | 根本到不了检查 |
| 单值图 `bar [10]` | **工具层已拦** | 同上 |
| 跑题 / 结论重复 | **整轮** | 结构性问题，没有定点修法 |

**10 个真实失败里，2 个能 auto-fix、5 个能定点、2 个在工具层就拦住了，
只有 1 个真需要整轮重来。** 现在这 10 个全部走整轮重来。

## 还没解决的硬伤：打分器和被打分的是同一个模型

调研里查到的公认结论：**self-preference bias——judge 给自己模型家族的输出
会虚高**，明确建议「never use the same model family as both generator and judge」。
我们正是这样：`muse-glimmer-30b` 既写又判。

三条可行的缓解（按成本排）：
1. **把 rubric 拆成离散检查**——正在做，而且被调研验证为标准缓解手段
2. **换个模型打分**：我们有 `gpt-5.6-luna`，打分只占一次调用，成本可接受
3. **pairwise 双向比较**代替打分——best-of 的场景天然适合

第 2 条是最直接的，值得单独做一次 A/B：同一批产出，本地模型打分 vs 换模型打分，
看两者对同一份产出的分歧有多大。**分歧大 = self-preference 确实在起作用。**
