## 这张表说明了什么

**M1 那三件——地基——是真落地了**，而且是这 107 批里质量最高的部分：提案层跨重启留着、
逐处和整层两种粒度、边缘记忆的误判率从 57% 打到 9%。

**而恰恰是最能决定「agent 是不是常驻」的两件，一件没做：**

- **3.5 的自动推进**（#7 的后半）：目录已经是计划了、每节有状态了，**就差「它自己往下走」**。
  今天 agent 仍然只在你按下按钮的那几十秒里存在——这正是方案 §1 自己写的那句
  「**默认状态下文档不知道自己要干什么，agent 只在你按下按钮的那几十秒里存在**」。
- **3.8 的注意力守卫**（#6）：完全没有。你切走再回来，接不上。

用户那句「不够深层次的 agent-native」，**指的多半就是这两件**——而不是缺什么新功能。

## 一个重要的约束（方案 §7 自己定的，别忘）

- **不做聊天框。** 「想加聊天框先问：这个意图能不能封装成按钮 + Doc Intent。」
- **不让 agent 直接改正文。自动推进也只产生提案。**
  ⇒ 这条是好消息：**提案层（M1 #2）已经落地了**，所以自动推进有地基可以站，
  不用先造安全网。这也是为什么 #7 是现在最该做的那一件。
- 不从标题 / 文体猜写作任务；不把材料塞进正文。

## 建议的下一件：#7 的后半（自动推进）

理由：
1. **前半已经在了**（目录 = 计划 + 每节状态），只差一个开关和「往下走」那条路；
2. **安全网已经在了**（提案层），符合 §7「自动推进也只产生提案」；
3. **它直接回应用户那句话**——agent 从「按一下动一下」变成「它一直在往前推」；
4. 它是**用户看得见的**：开关在目录上，每节状态会自己变，产出落进「改动」页签等你处置。

⚠️ 这一件的临界条件（照铁律 §1.3 先列全，做之前逐条填）：
没有骨架时开关能不能开 · 一节写完但判据没过怎么办 · 用户正在这一节打字时它推不推 ·
切走之后推不推（跟 #6 守卫缠在一起）· 模型报错 / 超时 / 没配 · 连续失败几次停 ·
提案堆到多少条要拦一下问人 · 关掉 app 再打开还推不推。

- **补 M1 #1 / M2 #4 / M3 #8 那几个「部分」**：先核清楚缺什么再说；它们不改变
  「agent 是不是常驻」这件事。
