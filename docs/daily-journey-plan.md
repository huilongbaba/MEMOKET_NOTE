# Daily Journey：把屏幕上发生的事变成可回顾的记录

> 用户 2026-09-14 提：定期截屏 → 分析内容 → 转成「在做什么」的描述 → 形成有深度的
> 日报；并且能回顾一段时间、汇总成跨时间的深度报告。
>
> 这份文档只出方案，不改代码。

## 0. 一句话的设计主张

**不要做成一个新子系统，做成一个新的「摄入来源」。**

这个产品已经有一整条链路：素材 → 摄入（分块、抽事实、断点续传）→ 知识库
（主题 / 实体 / 时间线 / 最近摄入）→ 定期回顾（`POST /api/compose/digest`：
一段时间的事实 → 核心结论 / 关键决定 / 待跟进 / 值得注意的变化）→ 写作 harness
（长报告，每句带引用编号）。

屏幕活动只要变成**跟会议记录同形状的东西**（一段时间 + 一段文字 + 一个 session id），
上面那一整条就全部免费复用：

| 用户要的 | 现成的东西 |
|---|---|
| 「今天我在做什么」的日报 | `digest(days=1)` |
| 「这两周我在做什么」的跨时间报告 | `digest(date_from, date_to)` |
| 只看屏幕活动 / 不看屏幕活动 | `kb/scope.py` 加一档（现在是 全部 / 笔记 / 会议记录 / 导入） |
| 报告有据可依、点得回原始记录 | 事实 id + 引用体系 + `kb:unit:` 页 |
| 深度报告（不止摘要） | 写作 harness（14 条判据都在） |

**要新写的只有「屏幕 → 一段文字」这一段。** 这是这份方案的全部工作量所在，
也是全部风险所在。

## 1. 先说隐私，因为它决定了其余所有设计

截屏跟录音不是一个量级：麦克风录的是你说的话，屏幕录的是**你看到的一切**——
密码管理器、银行、别人发给你的私信、还没公开的东西。这个功能一旦默认开着，
它就是这个产品里风险最高的一块。下面几条不是「加固」，是**前提**：

**① 不做「默认开」，做「第一次用时的一次真正的知情选择」。**
用户原话是「默认记录」。我建议不这么做，理由不是保守：macOS 的屏幕录制权限
**本来就会弹系统对话框**，你不可能真的「静默默认开」。既然那一刻一定会被打断，
不如把它变成一个说清楚的选择页——写明「记什么、存哪、留多久、谁看得到、
怎么关」，用户点「开始」才开始。这比偷偷开着更容易让人一直开着。

**② 黑名单优先于白名单，且默认非空。**
默认排除：密码管理器（1Password / Keychain）、银行与支付类、系统钥匙串、
浏览器隐私窗口。命中黑名单时**连描述都不产生**，不是产生了再删。

**③ 图片默认不留。**
描述做完就删原图，只留一张 256px 长边的缩略图用于回看时认路（可关）。
理由是量：8 小时 × 每 30 秒 ≈ 960 张 × 约 300KB ≈ **300MB/天**，一个月 9GB。
留全图除了体积，还等于把风险留在磁盘上。

**④ 有一个随手能按的暂停，而且它要显眼。**
菜单栏图标（录制中 / 已暂停两种状态）+ 一个「暂停 1 小时 / 到今天结束」。
锁屏、屏保、切到黑名单应用时自动暂停。

**⑤ 删得干净。**
删一天 / 一段时间时，要连带删掉它在知识库里抽出来的事实和 unit——否则
「我删了那天的记录」是假的。这条要写成测试。

**⑥ 本地模型这条路要留着。**
设置页本来就有「本地模型 / GPT」两档。屏幕描述这一步应当**可以指定只用本地
模型**，让「我的屏幕不出这台机器」是一个可选的真实承诺，而不是一句安慰。

## 2. 采集：贵的东西不要每次都做

朴素做法（每 30 秒截一张、每张都送视觉模型）在成本上不成立：960 次视觉调用/天。
分四层，**越靠前越便宜，绝大多数帧应该在前两层就被处理掉**：

**第 1 层 · 免费信号（不截图）**
前台应用名 + 窗口标题，macOS 原生 API 就有。`Xcode — MemoketApp.swift`、
`Chrome — 飞书文档 · Q3 复盘`、`Terminal — pytest` ——**光这一条就能回答大半个
「在做什么」**。每 5–10 秒采一次，几乎零成本。

**第 2 层 · 变化检测（截图但不外发）**
截图后算感知哈希（dHash / aHash），跟上一帧比。差异小于阈值 = 你还在看同一个
东西，丢掉。一天里大部分时间屏幕是不动的。

**第 3 层 · 分段（把连续的相似帧收成一段）**
「9:12–10:40 在 Xcode 里改 MemoketApp.swift」是一段。**分段是这个功能的核心
数据结构**——描述的单位是段，不是帧。切段的触发：应用切换、窗口标题实质变化、
画面差异超阈值、或超过上限时长（比如 20 分钟强制切）。

**第 4 层 · 描述（视觉模型，一段一次）**
每段挑 1–3 个代表帧（段首、变化最大处、段尾）送模型，产出**一段中文描述**：
在做什么、涉及什么项目 / 人 / 文件、有没有明确的动作或结论。

预期量级：一天大概 30–80 段，也就是 **30–80 次调用**，不是 960 次。
**这个数字必须先实测再定稿**（见 §6）。

## 3. 落地成什么：跟会议记录同形状

一段 = 一次 `ingest_text`：

```
session id   screen-<YYYYMMDD>-<段序号>        # scope 靠前缀识别
title        09:12–10:40 · Xcode · MemoketApp.swift
date         2026-09-14
content      这一段在 Xcode 里改 MemoketApp.swift，主要在调
             录音权限的申请流程……（模型产出的描述）
source       screen
```

进去之后它跟一场会议记录没有区别：抽出事实、挂到主题和实体上、出现在时间线和
「最近摄入」里、可以被召回、可以被写作时引用、可以被 `digest` 汇总。

`kb/scope.py` 加一档：`SCOPES` 增加 `"screen"`，`classify()` 认 `screen-` 前缀，
`SCOPE_LABEL` 加「只看屏幕活动」。右栏「记忆范围」下拉自动多一项。
**默认范围要不要包含屏幕活动，是个值得单独想的问题**——我倾向默认包含，但
写作时的「取材料」默认排除（屏幕活动噪声大，会稀释掉真正的材料）。

## 4. 报告

### 4.1 日报（今天）

`digest(days=1, scope="screen")` 就能出第一版。但**照搬现有的 DIGEST_SYSTEM
会出一份平庸的东西**——「今天你在写代码、开了几个会」这种话没有价值。
屏幕活动有它自己的形状，提示词要换，至少回答：

- **时间去哪了**：几大块、各多久（这是数出来的，不该让模型猜）
- **推进了什么**：哪些事有实质进展，依据是哪几段
- **卡在哪**：反复在同一处来回、或长时间停在一个报错上 —— 这类信号是屏幕
  记录**独有**的，会议记录和笔记里没有
- **计划外的**：今天真正花掉时间的事情里，哪些不在你原本的打算里

时长统计走代码不走模型（这个仓库的老规矩：能用规则算准的就不交给模型）。

### 4.2 跨时间报告

短周期（一周）：`digest(date_from, date_to)`，同一套。

长周期（一个月 / 一个季度）：**不要把 30 天的段直接灌给模型**——那是几十万 token，
而且会得到一份平均值式的废话。走两层：先对每天出日报（已经有了），再把
30 份日报交给**写作 harness** 写成长报告。这正是 harness 擅长的事：有骨架
（spine/beats）、每轮取材料、14 条判据盯着「有没有用上材料」「有没有引用」
「是不是同一组清单列了两遍」。

这一层的产出应该是**一篇笔记**，落在树上，可以继续编辑、继续续写。

## 5. 要动的地方（改动清单）

### 桌面壳（`desktop/`）

- `src/capture.ts`（新）：定时器、前台应用/窗口标题、`desktopCapturer` 截图、
  感知哈希、分段状态机。**只产出段，不做描述**——描述要花钱，归后端管。
- `src/main.ts`：菜单栏 Tray（录制中 / 已暂停）、暂停菜单、锁屏事件
  （`powerMonitor` 的 `lock-screen` / `unlock-screen`）。
- `package.json` 的 `extendInfo` 加 `NSScreenCaptureUsageDescription`
  （现在只有 `NSMicrophoneUsageDescription`，第 58 行）。

### 后端（`backend/app/`）

- `routers/journey.py`（新）：
  - `POST /api/journey/segment` —— 壳把一段（时间、应用、标题、代表帧）交上来，
    后端描述 + 走 `ingest_text` 入库
  - `GET /api/journey/day?date=` —— 某天的段列表（时间轴 + 缩略图）
  - `POST /api/journey/report` —— 日报 / 区间报告
  - `DELETE /api/journey/day?date=` —— 删这一天，**连带删事实和 unit**
- `database/kb/scope.py`：加 `screen` 一档
- `harness/prompts/`：`JOURNEY_DESCRIBE_SYSTEM`（看图说「在做什么」）、
  `JOURNEY_DIGEST_SYSTEM`（日报，替换通用的 DIGEST_SYSTEM）
- `database/store.py`：`journey_segments` 表（段的元数据 + 缩略图路径 + 对应的
  session id），以及黑名单 / 开关 / 保留天数落在 `provider_config` 同一套里

### 前端（`frontend/src/`）

- 左栏启动栏一个入口 → 「今天」页：时间轴 + 每段一行 + 日报在顶部
- 设置页一块「屏幕活动」：总开关、黑名单、保留天数、用哪个模型、删除某一天
- 右栏「记忆范围」自动多一项（scope 改完就有）

## 6. 我建议的做法顺序：**先做一次一小时的实测，再定稿**

这个功能有三个数字现在是猜的，而它们决定设计对不对：

1. **一天多少段？** 30 段和 300 段是两种产品。
2. **一段描述值多少钱？** 决定它能不能一直开着。
3. **描述有没有用？** 这是最要紧的一条——如果模型看着一屏 Xcode 只会说
   「用户在使用代码编辑器」，那整个功能就是个花钱的噪声源。

所以第一步不是写功能，是写一个**一小时的采样脚本**：真在你自己机器上跑一小时，
把段切出来、描述出来，然后**把产出读一遍**。这个仓库最近三十轮反复验证过一件事
（memory 里 `writing_harness_measurement` 那条）：**聚合指标找不到问题，读产出才能**。

读完再定：阈值、分段粒度、描述提示词、以及这个功能到底值不值得做成默认。

### 分期

| 期 | 做什么 | 能验证什么 |
|---|---|---|
| **P0** | 一小时采样脚本（不入库、不进界面），产出一份 markdown | 段数、成本、描述质量 |
| P1 | 壳里的采集 + 分段 + 菜单栏开关 + 黑名单 + 本地落盘 | 常驻稳定性、耗电、隐私开关是否够用 |
| P2 | 入库（`screen-` session）+ scope 一档 + 「今天」页 | 跟知识库融合得好不好 |
| P3 | 日报（专用提示词 + 代码算时长） | 日报有没有价值 |
| P4 | 跨时间报告（日报 → harness 长报告，落成一篇笔记） | 长报告有没有价值 |

P0 之后就该停下来一起看产出，再决定 P1 要不要做、怎么做。

## 7. 我现在就想说清楚的三个风险

**① 描述质量是成败所在，而它很可能一开始很差。**
「在使用浏览器」这种描述一文不值。要做出价值，描述里必须带**具体的东西**：
文件名、函数名、文档标题、对话里的人名。这跟这个仓库已经打过的仗是同一场——
写作 harness 里 `material_used` 那条判据就是为了对付「干净的通用文章」。
屏幕描述也要有同类的判据：**一段描述里没有任何具体名词，就判它没用，不入库**。

**② 常驻进程的稳定性和耗电。**
这是这个应用第一次有「一直在后台干活」的东西。截图、哈希、定时器都要有上限
和退避；空闲（无输入）时降频到几分钟一次；电池模式下降频或暂停。

**③ 它会把知识库的噪声抬高一个量级。**
一天 30–80 段，一个月上千条事实，很快会超过会议记录。所以：写作取材料默认
**排除**屏幕活动，召回时给它更低的权重，`scope` 的默认值要重新想一遍。
这一条如果不处理，「写作时右栏浮现的相关记忆」会从有用的会议结论变成
「你上周二在看某个网页」。
