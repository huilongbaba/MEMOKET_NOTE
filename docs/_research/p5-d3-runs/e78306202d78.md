午餐会上一定会有人问：交互断点明明在硬件侧，为什么不改硬件？答案是先把验证范围收敛到录后数据流，而不是把销售窗口前的验证重新扩大成硬件重做。已知计划显示，4月10日前后有一项交付节点；项目随后仍要按KO、EVT、T0、DVT、PVT和MP等阶段推进，具体结论取决于后续评估。更稳妥的路径是：在销售窗口前，先把录制后的数据处理与交付链路列为独立验证项，再依据评估结果决定是否扩大硬件改动范围。

这个取舍也应放回项目的实际开发节奏中判断：项目包含硬件、固件和App，并按KO、EVT、T0、DVT、PVT和MP推进，目前已从KO进入正式开发阶段。由于官网销售预计在6月末或7月开始，录制后的数据流转应作为并行验证项推进；是否调整硬件，则应由后续评估结果决定，而不能在没有测试依据时直接断言重做硬件会拉长周期。

## 数据流转译如何落地

午餐会的讨论焦点会很快落到自动化边界。这里不应把“自动转码、摘要、标签匹配、分发”或“教师只在群内修正”写成已经确认的产品能力和协作方式。更准确的写法是：把录制结束后的处理拆成待验证的步骤，并为每一步设置责任人和通过条件。首轮试点只需确认素材是否成功生成、是否能被送达指定协作位置、是否有人完成校正并继续使用；至于摘要程度、标签规则和协作载体，应在试点前明确，不宜直接写成 Memocad 或 Discord 已经确定。

```mermaid
flowchart LR
A[教师完成现场录制] --> B[系统自动转码与摘要]
B --> C[按课程标签匹配共创群]
C --> D[素材与摘要进入Discord]
D --> E[沉淀到案例库]
E --> F[跨校教师继续补充与复用]
```

试点时还要把异常路径一起验收，否则“自动”只在顺利录制时成立。录制结束后，系统需要给出明确的处理状态：已完成转码、摘要生成中、已推送共创群，或需要人工补发。触发失败时，责任不应落到教师身上，而应由试点负责人看到异常并补发；教师只需在 Discord 内确认内容是否适合继续讨论。

- 试点负责人：提前维护学校、课程、主题与 Discord 共创群的对应关系；
- 系统侧：负责录制结束后的转码、摘要、标签匹配和分发，并保留原始素材；
- 教师：只在群内补充术语、修正结论或标记可复用片段；
- 案例库维护者：将经过讨论确认的内容标记为可复用案例。

这样验收的对象就从某个单点功能变成了责任链：**系统负责把素材送到正确的位置，教师负责校正内容，案例库负责留下最终版本**。若其中任何一步仍要求教师回到手机端手动搬运，这次试点就只能算录制成功，不能算协作闭环完成。

这条链路的验收不以“系统生成了一份摘要”为终点，而以**另一位教师能否据此继续工作**为终点。若跨校教师能够从群内素材直接准备下一次课程或研讨，说明共创内容已经从一次性记录转成了可接续的教学资产；若仍需回到个人设备重新下载、改名、整理，再交给下一位教师，说明手动搬运只是换了位置，并没有真正消失。

因此，午餐会结束时需要留下的不是“同意试点”四个字，而是一次具体试点的最小配置：参与学校、课程主题、驻场教师、Discord 目标群，以及谁负责处理转码或分发异常。学校和课程可以先选一组，不必等待所有课程都接入；但这组内容必须能同时覆盖现场录制、跨校补充和案例库复用三个环节。

试点启动前，还要明确一条失败判定：只要教师仍需手动下载、改名、上传，或跨校教师无法从群内素材继续准备下一次课程，就不能把结果记为闭环完成。若摘要质量不足，先保留原始录音和群内修订记录，再调整摘要提示或标签规则；不要为了证明自动化有效而跳过人工校正。这里需要补上实际试点学校、课程主题和参与教师名单，才能把这条验证链路从方案变成可执行安排。

午餐会上还需要确认试点结束后交付什么，避免最后只留下“功能已开通”的结论。一次端到端试点至少应产生三类结果：一份带课程标签的原始录音与摘要，一条在 Discord 共创群内完成修订的讨论记录，以及一份被另一位教师实际取用的案例版本。

午餐会上还要把“谁触发”说成系统动作，而不是笼统地写成系统自动处理：教师结束录制并完成设备同步后，系统以录制结束事件触发转码；转码完成后生成初步摘要，并从预先绑定的学校、课程和主题标签中选择目标 Discord 共创群。试点负责人只需在启动前完成绑定，不在每次录制后临时指定去向。验收时由系统记录触发时间、处理状态、目标群和异常补发结果，教师则在群内留下第一次修订。这样既能确认素材确实被送达，也能区分是触发失败、标签匹配错误，还是摘要需要人工调整。

试点场景可以设为一次现场录制后的端到端验证，但应把它写成拟议方案而非已确定安排：一名参与者完成录制，系统或负责人员记录素材生成、处理、交付和后续使用的每个节点；另一名参与者依据交付内容进行补充或校正，最后检查内容是否被再次取用。协作平台、课程标签、参与人员和案例库字段，都应在试点启动前确认，不能直接预设为 Discord 或某个已存在的案例库。

午餐会上还应把试点结果对应到下一步决策，而不是只记录“已完成验证”。如果录制、转码、标签分发和群内协作均能跑通，但摘要仍需少量人工修订，结论应是保留现有硬件、继续优化规则；如果录制后的素材无法稳定进入目标群，结论就应集中到触发、状态回传和异常补发，而不是泛化为“整体体验不够好”。

建议会后只保留一张试点结果表，记录同一份素材的四项状态：是否成功触发、是否完成转码与摘要、是否进入正确的 Discord 群、是否被下一位教师实际取用。每项只写通过、未通过和具体异常，不再用“基本可用”这类无法推动决策的表述。这样到下一次评估时，可以直接判断是继续扩大课程范围，还是先修复某个环节。

试点复盘时重点记录两类偏差：一类是系统把素材送错群、漏发或状态不清，另一类是摘要遗漏课程术语、行业背景或关键结论。前者归入数据流问题，后者归入摘要与标签规则问题，不能混在一起评价。这样，即使第一次驻场共创没有得到完整案例，也能明确下一轮应修哪一段，而不是把所有问题重新归因于硬件体验。

现场演示不应只播放一段已经处理好的录音，而要从教师按下结束录制开始计时，完整走一遍真实链路。教师结束录制后，试点负责人只观察系统是否触发、状态是否回传；跨校教师直接进入目标 Discord 群完成补充；案例库维护者最后从群内标记内容中生成可复用版本。每个角色都按自己的实际动作参与，不能由同一个人代替所有环节，否则无法暴露权限、通知或交接上的断点。

如果这次驻场共创能够完成从现场录制到跨校教师取用案例的闭环，下一步就扩大到跨校联合研讨；如果失败，则按最后一个成功节点定位问题。例如素材已生成摘要但没有进入目标群，就暂停扩大试点，先修复分发与异常补发；若已进入群但无人愿意继续使用，则需要回看课程标签、摘要结构和案例库取用方式。这样，6月末或7月销售前要验证的不是一个抽象的“AI能力”，而是教师是否真的愿意沿着这条链路继续协作。[terrence-1439-0F4]

试点结果还应被整理成销售窗口前可以反复演示的一条素材链，而不是只在内部会议里口头汇报。演示时保留同一份录音的四个版本：原始录音、系统摘要、Discord 群内修订稿和最终案例卡片；每一步都显示前后关系，让学校看到教师如何从一次共创继续接力，而不是只看到一个孤立的摘要页面。

这样，6月末或7月开始销售时，产品展示的重点就不再是“设备能不能录下来”，而是**录下来的内容能否进入课程协作并再次被使用**。[terrence-1439-0F4] 如果试点尚未跑通，销售材料不能把自动分发描述成已完成能力，只能展示已经验证的部分，并把未通过的环节列为后续版本范围。

午餐会上可以把确认动作压缩成一次现场演练：先由教师完成一段课程录制，再由系统按预设课程标签触发处理；试点负责人当场查看素材是否进入目标群，另一位教师直接在群内补充术语或标记可复用片段，最后由案例库维护者确认是否形成可再次取用的版本。这样确认的不是某个功能按钮，而是三个交接点是否连续：录制结束后有没有触发，内容处理后有没有送达，送达后有没有人继续使用。

会议记录里只需要保留这次演练实际出现的异常和对应处理人。例如标签没有匹配到目标群，就记录为分发规则问题；摘要完成但状态没有回传，就记录为状态通知问题；内容进入群后仍需重新下载整理，则记录为交接未完成。**只有当原始素材、处理结果、群内修订和案例版本能够互相对应时，才能把这次驻场共创作为销售前可复用的验证样本**。
