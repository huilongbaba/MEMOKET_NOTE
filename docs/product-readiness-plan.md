> 第 768 轮起。**这是执行计划，不是方案。** 台账：`docs/TRACELOG-product.md`。
> 起因是用户第 768 轮的四点批评（原话逐条记在 §0）。上一个 200 轮
> （`harness-upgrade-plan.md`，批 1–28）做出来的是量具、闸和台账——
> **没有一条被证明让用户拿到的笔记变好了**。批 28 花 2.1M token 把
> `factual_grounding` 判 0 率从 48.1% 量到 48.7%，是这件事最诚实的注脚。

## 0. 用户原话（第 768 轮）

1. **稳定性很差**：a. 有时有引用，有时无引用；b. Skill 有时能加载，有时无法加载；
   c. 导出到飞书、Notion、Obsidian 好像从来没有验证过；d. 记忆随着正文浮现——
   光标点到哪里，会有哪些查询？编辑器里的一个点（绿色、黄色）代表的是一行还是一段？
2. **容错根本没做**：右键自定义，用户输入为空怎么办？智能插图，note 完全空白怎么办？
   **好好查一下这些功能的临界条件、容错处理。**
3. **整个 UX 不是一个合格的编辑器，不够深层次的 agent-native**。
   例：正文还有灰色字，根本不便于阅读。
4. **功能做得非常差**：脉络梳理的准确性？记忆的准确性？Harness 写作的效果？
   「我让你做了很多轮调研，根据调研结果针对性地提升 harness，怎么感觉毫无作用呢？」
   **边调研、边实验、边验证解法。**

## 1. 这 1000 轮的铁律（跟上一个 200 轮不同的地方加粗）

1. **每一批必须有「用户看得见的前后对比」**——截图、或一段用户能自己重放的操作。
   内部指标（判 0 率、命中率、突变验）**只是过程，不是交付**。台账里没有前后对比的批，
   不算做完。
2. **先复现，再修**。用户说「有时有、有时没有」，第一件事是找到那个「有时」的条件，
   写成能重放的用例；找不到条件就写清楚试了哪些条件。
3. **修一个功能之前，先把它的临界条件列全**：空输入、空正文、无选区、无知识库、
   离线、后端没起来、模型报错、超时、重复点击。每一条要么有处理、要么明确写「不处理，因为…」。
4. **不再写调研文档。** 需要查行业解法就查，直接写进那一批的台账「依据」一栏，
   然后在同一批里实验和验证。
5. 上一个计划的规矩照旧：能用代码判准的不交给模型；闸跑绿不等于闸有用（突变验）；
   顺手量出来的数当分母前先逐条读；**绝不碰用户真实笔记**（`db_guard`，两份库，
   基线 482 行 / `47dcc54be60aa4f2`）。
6. **每一批的台账要有「用户会怎么发现这个问题」一栏**——如果一个改动用户永远发现不了，
   它排在后面。
