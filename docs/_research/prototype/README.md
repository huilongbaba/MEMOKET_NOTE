# 架构原型

`harness-framework.md` 那套类型和循环的**可执行版本**，零依赖、假 LLM、假工具。

```bash
cd docs/_research/prototype && python3 test_harness_proto.py
```

它不是实现，是**架构的验证**：如果这 11 个场景跑不通，说明架构在纸上说得通、
写起来不通。实际上它当场抓到了一个缺陷——见下面第 ④b 条。

| # | 场景 | 验证什么 |
|---|---|---|
| ① | 第 2 轮全达标就停 | `complete` 提前终止 |
| ② | 第 2 轮最好、第 3 轮变差 | **跑满轮数交付 best，不是最后一轮** |
| ③ | 检查连命三轮 | 命中就跳过打分（`evaluate` 一次没被调） |
| ④ | 标题层级过浅 | auto-fix 修好后不打回 |
| ④b | fix 修不好 | **修完仍不合格就回滚，不留副作用** ← 原型抓到的设计缺陷 |
| ⑤ | 一个 middleware 抛异常 | 隔离成 warning 事件，run 照常完成 |
| ⑥ | 第 1 轮写完就断线 | 已有内容仍然落盘 |
| ⑦ | 跑 8 轮、budget=3 | 材料累积且有上限 |
| ⑧ | 前两次取材料查不到 | `wrap_prepare` 能重试 handler |
| ⑨ | 缓存命中 | `wrap_prepare` 能短路（handler 根本不调） |
| ⑩ | 两个 wrap | 洋葱：第一个包住其余，`A-in B-in B-out A-out` |

**④b 是写原型换来的**：原来的 `fix` 逻辑是「修完再 check，还命中就打回」，
但那次失败的 fix **已经改了 `st.content`**——下一轮基于被改坏的内容继续。
正确做法是修完先在副本上验，通过才采纳。纸上推演三轮没发现，跑一次就出来了。
