### ⑤ 91% 的模型时间在 harness 上，而且看不出花在哪一步

```
feature                  次数     总秒   中位秒  P90秒   入token中位  出token中位
note-harness/run          417    2881     4.6   15.4      10537         184
writing-plan/run          471    2610     4.1   10.0       4381         145
（其余 13 项合计）           92     675
```

**入 10537 / 出 184 ≈ 57:1。** 而 `feature` 是在 `main.py:114` 按 HTTP 路由打的标，
一次跑里的续写、打分、工具规划、修订**全叫同一个名字**——
「打分占了多少预算」这个问题现在答不出来。

### ⑥ 每一轮的分数跑完就没了

`loop.py:130` 把 `CUSTOM_EVALUATE` 发进 SSE，`middleware/history.py` 只落**最后一轮**。
`harness_snapshots` 只在「等用户确认」时写。
于是「第 3 轮比第 2 轮好吗」这个问题，**在现有数据里无法回答**。

### ⑦ 打分和写作是同一个模型、同一套配置

`provider_config` 只有一个槽（实测当前是 `gpt-5.6-luna`），
`util/llm.py` 每处都走 `store.get_active_llm_config()`。
`checks/__init__.py` 的开头自己写着这件事：
> The scorer and the thing being scored are the same local model, so its
> blind spots line up exactly with the writer's.

## 2. 七处改法（按证据强度排）

### P1 段内重复没有任何人管 —— 直接对应 ③④

**证据**：42.9%。**机制**：这个系统里每一处查重都是**段落级**的。

| 位置 | 切法 |
|---|---|
| `harness/middleware/repeats.py:57` `_paragraphs` | `text.split("\n\n")` |
| `editor/outline.py:264` `drop_already_written` | 按段 |
| `harness/checks/structure.py:143` `no_repeated_lists` | 按清单块 |

而这次重写落在**同一段内部**（连空行都没有），三条全部看不见。
`drop_already_written` 的注释里写得明明白白「模型这一轮把整节重写了一遍，
于是新旧并存」——诊断是对的，**只是切得不够细**。

**改动清单**
- `harness/middleware/repeats.py`：`find_repeats` 增加一趟**句级**扫描，
  同段内两句相似度超阈值就产出 `DupHint`。段级那趟保留（跨段重复还是要抓）。
- `editor/outline.py:264`：`drop_already_written` 插入前同样按句再剔一遍。
  这是「确定性手段，不指望模型自己不重复」那条路子的延续。
- `harness/checks/structure.py`：新判据 `no_restated_paragraph`，
  段内重复字数占该段 ≥25% 时打回。

**阈值不要拍脑袋**：句级查重最容易误伤排比和有意复述。
先在这 18 篇上跑分布（跟第 601 轮定 `drop_already_written` 的 0.62、
第 609 轮定顿号清单 0.7 同一个做法），再定数；
**误伤比漏报贵**——删掉一句真内容用户看不出来。

### P2 跨「跑」没有任何护栏 —— 直接对应 ③

`middleware/best_of.py` 只在**一次跑内部**挑最好的那一轮；`loop.py:299` 的
`_regressed` 也只看本次跑。用户第二次点「跑」的时候，起点是上一次跑留下的
正文，而**没有任何东西比较「这次跑完是不是比上次差」**。
9→6→4 就是这么来的。

**改动清单**
- `harness/middleware/history.py:32`：`RunRecord` 增加正文长度和 `content_sha`。
- `harness/middleware/save.py`（提交前）：跟 `recent_harness_runs(key, 1)` 比一次。
  明显更差（沿用 `State.rank` 的口径）时**不静默覆盖**——
  这跟「删一段要墓碑不抠数组」是同一条规矩：不可逆的动作要让用户看见。
  最小落地是发一个 `CUSTOM_WARNING`，正文照旧存（留退路给用户自己判断）。
- **先别做自动回滚。** 样本只有三篇，而回滚错了比多一段重复严重得多。

### P3 每轮分数落库 —— ⑥，也是后面所有优化的前提

没有这张表，P1/P5/P6 改完都没法说「确实变好了」。

**改动清单**
- `database/store.py:270` 旁边加 `harness_rounds(run_id, round, scores, content_len, ms)`。
- `harness/middleware/history.py` 从 `after_run` 扩到 `after_judge`（每轮写一行）。
  修剪规则跟 `harness_runs` 一样（每个 key 留最近 50 次跑）。
- 这张表要能直接回答三个问题：**第 N+1 轮相对第 N 轮，最弱维度变好了吗 /
  其它维度掉了吗 / 正文长了多少。**

### P4 `status` 记的是裁决，不是停机原因 —— ①

`history.py:32` 写的是 `st.ev.status`（`complete` / `continue` / `blocked`），
而**真正的停机原因在 `st.stopped`**（`max_rounds` / `stall` / `regressed` /
`awaiting_review` / …）。于是那 54% 的 `continue` 里，
「跑满轮数还没达标」和「连着几轮没动静自己停了」和「比最好那轮更差主动停」
**混成了一个值**——而这三件事该采取的行动完全不同。

**改动清单**：`harness_runs` 加一列 `stopped`，`history.py` 同时写 `st.stopped`。
一列的事，但它把 ① 那个数字从「知道有问题」变成「知道是哪个问题」。

### P5 有几个维度从不区分好坏 —— ②

`material_use` 25 次里 24 次满分；`follows_prompt` / `fits_context` /
`no_fabrication` / `table_validity` / `data_grounding` **100% 满分**。
它们每一轮都占着打分 prompt 的篇幅和输出预算，却从没驱动过任何一个动作。

**先别急着说这些维度写坏了。** `modes.py:183` 的 `_MATERIAL_USE` 写着
「没给材料就算达标」——**它满分很可能只是说明那些跑里根本没喂材料**，
判据本身是对的。这正是为什么 P5 必须排在 P3 后面：
分不清「判据不区分」和「这个条件很少出现」，就会把好判据删掉。

**也不能直接删**：`no_fabrication` 是安全网，样本只有 3 次不能证明它没用
（**这正是 `_corpus.mts` 那条空泛性防线要防的事**——在一个几乎不可能命中的
语料上得到 100% 通过，说明的是语料不对，不是判据没用）。

**改动清单**（顺序不能反）
1. 先落 P3，攒够每轮数据。
2. 再看这几个维度**有没有任何一轮打过 0/1**。真的从未区分过的，
   两条路选一条：措辞收紧（`modes.py:183` 起）到能区分；或者降级成
   `checks/` 里的确定性判据——**只在失败时说话，不占每轮的打分预算**。
3. `no_fabrication` 无论数据如何都留着。安全网的价值不按命中率算。

### P6 打分换一个模型 —— ⑦

`checks/__init__.py` 自己承认盲区重合。现在整个链路一个模型槽。

**改动清单**
- `provider_config` 加一组可选的 judge 槽（留空 = 跟主模型同一个，
  行为跟现在完全一致）。
- `harness/adapter.py:26` `AppLLMClient` 多一个 `role="judge"`，
  `util/llm.py` 按 role 取配置。
- **成本是可控的**：打分调用的输出中位只有 184 token（⑤），
  换一个更强的模型只在打分这一步花钱，写作那一步不动。

**这条要先做 A/B 再铺开**：拿同一批笔记跑两遍，比 P3 落下来的每轮分数。
「换个更强的模型打分」听起来一定更好——但这个仓已经吃过
「听起来一定更好」的亏（第 679–710 轮整段视觉适配对错了参照物）。

### P7 按步骤记用量 —— ⑤

`main.py:114` 按路由打标，一次跑里所有调用同名。

**改动清单**：`llm.ctx_feature` 在 harness 里按步骤覆写
（`note-harness/produce` / `judge` / `tools` / `revise`）。
`loop.py` 每一步本来就有 `Event.activity`，同一个位置顺手 set 一下即可。
改完立刻能回答：**打分占了多少预算、值不值那些钱**。

## 3. 明确不建议做的

- **不加「重复了就自动删」的自动修**。P1 只做到「打回 + 给出候选对」为止。
  这个仓的经验是确定性删除只在**机制明确**时才安全
  （`drop_already_written` 删的是「插入前就已经存在的整段」，边界很硬）；
  段内句级相似是**语义判断**，自动删会吃掉排比和有意复述。
- **不把 `max_rounds` 调大**。②③ 说明问题不是轮数不够——
  跑 3–4 轮的达标率（29%）比跑 1 轮（53%）还低。
- **不重写 `loop.py`**。它是十二个框架里唯一一份、已经被
  「一个 harness 有另一个没有」的 bug 教育过四次的代码。
  这七条全部落在 middleware、checks 和落库上，一行循环都不用动。
- **不把控制器交给模型**（`policy.py` 开头已经论证过：不可复现、无法归因）。

## 4. 改完怎么算有效

落地之后必须能回答的五句话，**每一句都要有数**：

| 判据 | 现在 | 目标 |
|---|---|---|
| 段内重复字占比（18 篇产出上量） | 中位 0%，最差 **42.9%** | 最差 < 10% |
| 反复跑同一篇，分数单调下滑的比例 | **3/6** | 0/6 |
| 收尾时还在 `continue` 的比例 | **54%** | — 先要能分清是哪一种（P4） |
| 打分占模型预算的比例 | **未知**（P7） | 知道 |
| 从不区分好坏的维度个数 | **≥5**（样本不足，P3 后再判） | 0（要么区分，要么降级） |

回归照旧：`npm test`（tsc + eslint + 254 vitest + 28 项脚本）、
后端 `pytest`（1119）。P1 的阈值要按 `_corpus.mts` 那条规矩验**空泛性**——
在真实语料上「一条都不命中」和「全部命中」一样说明判据没用。
