# 侧栏的信息架构：两套层级挤在一棵树里

> 用户 2026-09-14 提的三个问题，合起来是同一件事。这份文档只出方案，不改代码。
>
> 1. 知识库放在文件列表里合适吗？
> 2. 无限续写放在左侧栏好吗？
> 3. 文件列表不显示创建时间和来源好吗？

## 0. 一句话的诊断

**这个产品有两套层级——用户自己摆的（笔记树）和机器给出来的（主题 / 实体 /
时间线）——现在它们挤在同一棵树里，而这棵树只有一种排法（手动顺序）。**

三个问题各是这件事的一个侧面：知识库进树是「两套层级挤在一起」；无限续写放
左栏是「一个需要上下文的动作被放进了没有上下文的位置」；列表不露时间和来源是
「只有一种排法、又没有别的线索」。

## 1. 知识库放在文件列表里

### 现状

`GET /api/tree` 只返回真笔记（`store.tree()`，`backend/app/database/store.py:1345`）；
知识库那棵子树来自 `GET /api/kb/tree`，在前端跟笔记行合并成 `allRows`
（`frontend/src/App.tsx:623`），挂在树的最底下。展开一级要再取一次
（`loadKbChildren`，`App.tsx:587`）。

实测这个库（terrence，2026-09-14）：

| | 行数 |
|---|---|
| 树上真笔记 | **26** |
| 知识库子树 | **180**（还是实体懒加载之后的数字；实体本身 1214 个） |

知识库一级有 7 个：主题 / 实体 / 时间线 / 最近摄入 / 事实表 / 主题地图 / 定期回顾。

### 三条理由

**① 类别不同，规则相反。** 树是「我写的、我摆的」，知识库是「机器从材料里抽
的、机器摆的」。笔记能改名、能拖、能删；主题不能。用户对着 `# work 6034` 右键，
菜单里该有什么——这个问题现在没有好答案。

**② 体量倒挂。** 一个排在最底下的节点，装的东西比它上面所有东西加起来多一个
数量级（180 : 26）。视觉权重和信息权重正好反过来。

**③ 不合适已经在代码里留下痕迹了。** 需要这么多特例，通常说明它不属于这里：

- 第 175 轮得专门打补丁：实体超过 200 个不随树下发（391KB → 57KB）
- 第 615 轮的「实体栏只剩 3 个 chip」出在同一条链上（先截断后过滤）
- 虚拟 id 每加一种要同时改七处：`util/virtual.isKnownVirtual`、`App.openVirtual`、
  `needsFacts`、面包屑父链、`KbNoteView` 路由、`probes` 父链、`NoteTree.iconOf`
  （记忆文件里专门记了这条）
- 树行的 `fact_count` 字段注释写着「真笔记恒为 0」（`schemas.py:118`）——
  同一个结构里两种节点各用一半字段

### 但不能简单搬走

树上有知识库，承担着一件真事：让「我的材料」和「我的笔记」看起来在同一个空间
里，而不是一个外挂的搜索引擎。这是这个产品的立身之本，不能为了整洁牺牲掉。

### 三个选项

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| A | 保持现状，只把默认折叠做稳、加一条视觉分隔 | 改动最小 | 三条理由一条都没解决 |
| B | **树上留一行入口，不在树里展开**；下钻回知识库首页 | 两套层级不再交织；`allRows` / `loadKbChildren` / 虚拟 id 七处特例全部消失 | 「在树上一层层翻主题」这个用法没了 |
| C | 知识库完全移出侧栏，只留左栏一个图标 | 最干净 | 「同一个空间」的感觉也一起没了，退化成外挂搜索 |

### 推荐：B

理由是「写作时一键够到知识」这件事**已经有两条更好的路**——右栏的「记忆」面板
（跟着正文自动浮现相关事实）和 ⌘K（全局搜索含知识库）。树上这条是第三条路，
成本最高、收益最小。而知识库首页（搜索框 + 四个数字 + 月度图 + 主题 / 实体 /
最近摄入 + 事实表 / 主题地图 / 定期回顾 三个入口）本来就比在树里一层层展开好用。

留下的那一行不是妥协，是入口：它回答「我的材料在哪」，点进去才回答「里面有什么」。

### 改动清单（B）

- `frontend/src/App.tsx:623` `allRows` —— 不再把 kb 行并进树，只保留一行 `kb` 入口
- `frontend/src/App.tsx:587` `loadKbChildren` / `:648` `toggleKbNode` —— 删掉
- `frontend/src/App.tsx` `kbExpanded` / `kbChildren` 两个 state 及其 localStorage —— 删掉
- `frontend/src/components/NoteTree.tsx:51-60` `iconOf` 里的 kb 分支 —— 只留 `kb`
- `GET /api/kb/tree` 保留（知识库首页的下钻要用），`/api/kb/tree/children` 保留
- `probes.ts` 的 `kbexpand:` 探针改成在知识库页里验证下钻
- **不动**：`KbNoteView` 路由、面包屑、标签页——虚拟页照开，只是不从树上进

## 2. 无限续写放在左侧栏

### 现状

左栏那一列现在混着四类东西：

| 类别 | 按钮 |
|---|---|
| 建对象 | 新建、今日日记 |
| 导航 | 搜索 |
| 数据进出 | 导入 |
| 应用级配置 | 写作 Skill、设置 |
| **动作** | **无限续写**（`App.tsx:2878`，`bx-rocket`） |

无限续写是唯一一个「动作」，而且是**对某一棵子树**的动作。

### 位置的毛病已经用 bug 的形式暴露过一次

工具栏按钮天然没有上下文，这个动作天然需要上下文。第 611 轮实拍：站在一篇
**根笔记**上点它，程序只能猜你指哪棵子树——`openWritingPlan` 落到
`parents[0]`，树上第一个有子节点的行，在真实库里是自动生成的「09 月」日记
文件夹，对话框标题写着「09 月 · 写作计划」，跟手头的事毫无关系。

那一轮已经改成「猜不出来就开选择器让你挑」，但根子还在：**一个全局位置在替
一个局部动作做决定。**

### 它为什么会在左栏

原来放在文件夹标题栏的一个图标里，用户反馈「我找不到那个按钮了」——没有文件夹
时那个按钮在页面上根本不出现。所以真问题不是「该不该在左栏」，而是**文件夹那
一级的入口不够显眼**，只好拿一个全局位置去兜。

树的右键菜单里其实一直有（`App.tsx:848`「对这棵子树无限续写」），但右键菜单是
「知道了才会去用」的地方，不解决发现。

### 推荐（第 621 轮修正）

初版写的是「左栏按钮保留、但一次都不猜」。落地之后用户一句话戳破了：
**「文件夹右击就有，为什么还要有一个单独的按钮？」**——同一个动作当时有三个门，
而我自己前一节才刚论证过知识库「三条路里最差的那条该去掉」。

修正后：**砍掉左栏那个火箭。** 它是错配最深的一个——工具栏按钮天然没有上下文，
这个动作天然需要上下文；「一律问」只是把失手概率压低，没拔根。留下两个，各有各的活：

- **标题行的入口**（`.title-action`，带字）＝ **发现**。一直看得见，就长在它作用的
  那篇笔记身上，点了不用选也不用猜。给**所有真笔记**，不只文件夹——写作计划本来
  就是来建这些子笔记的（第 611 轮），只给文件夹的话，一个还没有层级的库根本看不见
  这个功能。
- **树上右键**＝ **指哪打哪**。要对别的子树跑时用，那是「知道了才会去用」的地方，
  本来就不承担发现。

### 顺带：名字

「无限续写」（对文件夹，生成分段、每段一篇笔记）和「智能续写」（对单篇，修订 +
续写交替）两个名字太像，光看名字分不出作用域。建议一并改掉——方向是让名字自己
说出作用域，比如「整理成几篇」/「把这篇写完」。**这条要用户拍板，文档里只提。**

### 改动清单

- `frontend/src/App.tsx:1016` `openWritingPlan` —— 去掉 `self ?? parent` 的推断，
  一律走 `askNode`；当前笔记有子节点时把它排在选择器第一位（是提示，不是替你决定）
- `frontend/src/App.tsx:2878` 按钮 `title` 改成「无限续写：挑一棵子树，一段接一段写」
- ribbon / 标题栏加文件夹级入口：`components/Ribbon.tsx`，条件 `child_count > 0`
- 名字：等用户拍板

## 3. 文件列表不显示创建时间和来源

### 现状比「不显示」还要更欠一点

**这两个字段压根没下发到树。** `TreeRow`（`backend/app/routers/schemas.py:97-119`）
带的是 `updated_at` / `ingested_at` / `cite_count` / `fact_count` / `pinned` /
`icon` / `child_count` / `branch_count`——**没有 `created_at`，没有 `source`**。
SQL 也没查（`store.py:1347`）。

它们只在「信息」那个 ribbon 页里有（`components/NoteInfoPanels.tsx:30` 创建、
`:35` 来源 · X 导入 · 本地改过）——你得先打开那篇、再点一个标签页。

**而且列表没有任何排序。** 树只按 `position`（手动顺序）排
（`NoteTree.tsx:84`）。知识库有「最近摄入」、日记按日期，**唯独笔记没有
「最近」这个概念**。

第 609 轮给撞名的行补时间，现在回头看那是个症状补丁：真正让人分不清那四篇
「创业一年回顾」的，是列表没法按时间看。

### 不主张直接加两列

一行已经扛着：展开箭头、图标、标题、撞名时间、事实角标、摄入角标、克隆角标、
子节点数。再塞两段文字，树就变成表了，而树的职责是结构。26 行不需要；300 行
需要的是**排序和筛选**，不是每行多两段字。

### 推荐，按价值排序

**① 来源用图标，不用文字。** 跟现有的 ⇡ 一样的成本——一个字形，不占宽度。
飞书 / Notion / Obsidian / 批量导入 / 写作计划生成的分段各一个。图标那一列
本来就在（用户能自选），导入时给个默认来源图标即可。

这个库现在 26 篇全是手写（`source` 全空），所以看不出差别；但一旦开始导入，
**「这行是我写的还是飞书来的」是唯一一个会改变你怎么读这行的信息**——它决定
你信不信里面的话、该不该直接改它。

**② 列表加一个「按最近」模式。** 切到这个模式时时间自然显示，因为那是这个
模式的重点；不切就不显示。它同时解决撞名和「我昨天写的那篇在哪」。

**③ 创建时间不上树。** 找东西的线索是修改时间（「我昨天动过的那篇」）；创建
时间只在信息面板里有意义。

### 改动清单

- `backend/app/database/store.py:1347` 的 SELECT 加 `n.source`（`created_at` 不加）
- `backend/app/routers/schemas.py:112` `TreeRow` 加 `source: str = ""`
- `frontend/src/api.ts` `TreeRow` 类型同步
- `frontend/src/components/NoteTree.tsx` `iconOf`：用户没自选图标时按 `source` 给默认图标
- 「按最近」模式：`NoteTree.tsx:84` 的 `list.sort` 按模式切；开关放侧栏搜索框那一行；
  按最近时不画层级（跟搜索时一样，`App.tsx:2914` 那条规矩：命中就该直接看到）
- 撞名日期（`util/dupTitles.ts`）在「按最近」模式下自动失效——那时每行都有时间

## 4. 落地顺序

三条彼此独立，但有个自然的次序：

1. **③ 的来源图标**——最小、最快见效，而且不依赖任何结构调整
2. **② 的「一次都不猜」**——两行改动，把第 611 轮那个 bug 的根拔掉
3. **③ 的「按最近」模式**——中等，做完之后第 609 轮的撞名补丁可以退休
4. **① 的知识库出树**——最大，会动 `allRows` / 两个 state / 七处虚拟 id 特例，
   建议单独一批做，做完当轮重打 dmg

**② 的文件夹级入口**和**名字**两条要用户先拍板再动。

## 5. 编辑区那四条（用户 2026-09-14 追问，第 618 轮）

> 「开始写... 支持 Markdown 和 ```mermaid 图表」这个说明语好吗？蓝色图标这个设计
> 好吗？这些 icon 用户不太好理解吧？`/` 怎么让用户知道？

### 先说根因：那些图标本来有字，只是从没露过面

`styles.css` 里原来有一条：

```css
@container (max-width: 600px) { .fb-label { display: none; } }
```

默认三栏（左 320 + 右 340），中间编辑区就是 600 上下——**除非关掉一侧面板，
否则那几个按钮永远只有图标**。而空文档的提示语写着「点右上角**「续写」**」，
指着一个看不见的标签。这不是取舍，是自相矛盾。

阈值降到 **380**（分屏对照的一栏那种真挤不下的宽度），正常用一定看得见字。

### 提示语

原文三个毛病：讲的是**实现细节**（支持 Markdown 和 ```mermaid）不是邀请；
` ```mermaid ` 这种写法是给程序员看的；而最值钱的东西一个字没提——`/` 后面挂着
**八个能力**（用 AI 写 / 智能插图 / 智能表格 / 图片转表格 / 数据可视化 /
智能数据分析 / 语音输入 / 插入音频）。空文档那一刻是**唯一一个用户愿意读提示
的时刻**，却拿去讲 Markdown 了。

换成：`写点什么…　输入 / 唤出 AI：用 AI 写、插图、表格、数据分析…`

Markdown / mermaid 的说明挪进「更多 → 正文怎么写」（指向 ⌘/ 那张快捷键表）——
它属于「想起来了去查」，不属于「第一次打开」。顺带给那张表补了 ` ```mermaid `
一行，不然又是一个指向空处的指路牌。

### 按钮的主次

原来「续写」「智能续写」「▾」三个连着的实心蓝，视觉上都是「主操作」——三个
一样响的按钮抢同一块地方，等于没有主次，而且它们浮在正文右上角、压着第一行
要写字的地方。

改成**只有一个实心蓝**（续写，最常用也最便宜的那个动作），智能续写和它的 ▾
降成描边（`.fb-btn.secondary`），麦克风和 ⋯ 保持朴素。跑起来时照旧变红。

### 状态

这四条已落地（第 618 轮），跟 §3 的来源图标同一批。
